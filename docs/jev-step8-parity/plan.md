# Jev による Step 8A/8B/8C 判定の置き換え検証計画

- 作成日: 2026-10-17
- 状態: 承認済み（範囲・合否基準・worktree）。Step 1 着手。

## 目的

`isometric-story-workflow` の Step 8A/8B/8C（現在は Opus の独立レビュー）を、Jev の事前判定で一部置き換えられるか検証する。主目的はトークン消費の削減。

## 前提

- Opus の判定を正解とはみなさない。Opus と Jev が食い違った項目は人間が判断し、その結果を正解として採点する。
- 合格事例だけでは評価できないため、過去に指摘を受けて修正した「修正前の画像」を必ず含める。
- 最重要の指標は見逃し率。Jev の判定が厳しすぎる側の誤り（問題ないものを不合格にする）は許容範囲を広く取る。
- Jev は実験的な画像入力機能（1.14、opt-in ヘッダー）を使う。Box（位置検出）は「見つからない」と答えられないため使わない。
- Jev の呼び出しには共通関数 `shared/jev/src/jev-client.mjs`（`askJev`）を使う。

## 対象データ

`/Users/sawairikeisuke/Documents/Blender/isometric/pomodoro_assets/` 配下の既存 2 ストーリー（読み取りのみ）。

- windmill-hill_story-01-windmill 系
- creature-watching_story-02-beehive 系

目標：不合格の事例を 15〜20 件以上含めること。

## 手順

1. **データ収集**：過去の Step 8 の証跡から「画像・観点・判定項目・Opus の判定・その後の修正の有無」を 1 行ずつ並べた表（`dataset.jsonl`）を作る。
2. **問いの設計**：8A と 8C は項目をそのまま Yes/No の問いにする。8B は過去の指摘を分類し、分類ごとに定型の問いを作る。
3. **実行**：Jev 1.14 で判定と確率を記録する。必要なら Opus 5.5 も同じ問いで判定し直す。トークン量と費用を記録する。
4. **採点**：食い違った項目を人間が判断したうえで、下の合否基準で評価する。
5. **判断**：観点ごとに置き換えの可否を決める。置き換えを認めた観点も、本番で数クール Opus と並行して動かしてから切り替える。

## 合否基準（承認済み）

| 指標 | 置き換えを認める目安 |
|---|---|

## Step 1 の結果（2026-10-17）

`dataset.jsonl`（50 行）= `collect_windmill.py`（19 行）+ `collect_beehive.py`（31 行）。

- 画像と判定の対応（`pairing`）
  - `verified_by_mtime`（19 行）：Windmill クール3 の 2 回目のレビュー。画像の更新時刻が 1 回目と 2 回目のレポートの間にある。1 回目の画像は上書きされて残っていない。
  - `inferred_medium`（13 行）：Beehive の `step8_pre_r8/`（08-22 14:01）と 8A 第 1 ラウンドの記録（同日 14:34）。
  - `inferred_low`（18 行）：Beehive の 8A 第 3 ラウンド（ハッシュが別セット）と、最終セット `step8/`（合格記録より後にレンダーされたもの）。
- Beehive の記録に残るハッシュは、現存する画像セットのどちらとも一致しなかった。
- Opus が不合格とした行は 15 行。そのうち 5 行は親の実測で誤りと確定（`measured_false`）。別に、単発の指摘が実測で正しいと確定した行が 2 行（`measured_true`）。
- **確度の高い実欠陥は約 12 件で、目標の 15〜20 件に届いていない。** 8A は Windmill の記録がなく、Beehive だけ。

## Step 2 の結果（2026-10-17）

`questions.jsonl`（50 行）を `build_questions.py` で生成。API はまだ呼んでいない。

- 各行に Noul の問いを 2 つ付けた。
  - `specific`：記録された指摘・条件そのものを問う（Opus との直接比較用）。
  - `generic`：指摘内容を知らない本番を想定した、分類ごとの定型の問い。

- Box は使わない。
