# Skill が前提にする能力と実行確認

この文書は `auditing-wcag`、`reviewing-a11y`、`ship-learn-next` の指示を、現在の実行環境で確認できた能力と区別して扱うためのローカル参照である。外部 Skill の本文や `allowed-tools` は変更しない。

## 証拠の区分

| 区分 | 意味 | 言えること |
|---|---|---|
| 文書上の要求 | Skill や参照文書に能力名・操作例が書かれている | その Skill が要求・想定する能力が分かる。実行環境にあるとは言えない |
| メタデータあり | 現在のツール一覧に呼び出し口が掲載されている | 呼び出し口が公開されている。対象ページで成功したとは言えない |
| 実行確認済み | 対象と目的を定めた呼び出しが成功し、結果を確認した | その対象・時点・操作の範囲で実行できた |
| 条件付き | 準備、許可、対象データ、接続など前提が揃ったときだけ使える | 前提と結果を記録できるまでは能力を使えたと扱わない |
| 未確認 | 現在のメタデータや実行結果で確認できない | 利用不可とも不存在とも断定しない。確認できなければ制限を記録する |

現在一覧に名前があることを、ページ・ファイル・対象フローでの実行証拠に置き換えない。能力を実際に使ったという報告には、対象、実行した操作、時刻または対象版、結果、必要な出力・証跡を添える。失敗、未実施、結果の読み戻し失敗は成功として数えない。

## 正式なWCAG適合監査

`auditing-wcag` は、対象レベルとページ範囲を定めたうえで WCAG 2.2 の対象となる A/AA 成功基準を一件ずつ判定する。coverage matrix に載る全基準を報告し、各行に `Pass`、`Fail`、`NT`、`NA` のいずれか、根拠、判断理由を付ける。自動ツールが成功しても監査全体の適合を意味しない。スクリーンリーダー確認や支援技術とブラウザーの組合せ確認は別途範囲に含めない限り未実施である。

| 判定 | 使う条件 | 必須の説明 |
|---|---|---|
| `Pass` | 対象基準を満たすことを示す、範囲に適した証拠がある | 対象箇所、観察・操作、根拠。自動結果だけの場合はその検査範囲も示す |
| `Fail` | 対象範囲で基準違反を示す証拠がある | 失敗条件、対象要素・フロー、証跡 |
| `NT` | 未実施、能力・アクセス不足、実行失敗、結果不足などで判定できない | 理由コードまたは具体的理由、足りない証拠・操作、次の確認担当者（owner）。保留項目として列挙する |
| `NA` | 対象範囲を十分に確認し、その成功基準が実際に適用されない | 適用されない根拠と、確認したページ・フロー・コンテンツ範囲。未調査・取得失敗・見つけられなかっただけでは `NA` にしない |

基準ごとの操作と記録を区別する。たとえば `2.1.1` と `2.1.2` はキーボードのみの操作記録、`2.4.3` はフォーカス順序、`2.4.7` はフォーカス可視性の証拠を要する。画像・DOM・アクセシビリティツリーは実際のキー操作の代わりにならない。キー操作能力がないか実行していない場合は該当基準を `NT` とし、操作が可能なブラウザー環境を次の owner に指定する。

`NT` は「違反なし」でも「適合」でもない。レポートには対象レベル、ページ・フロー、端末やブラウザー、除外範囲、使用・未使用ツール、未解決項目を記載する。出力形式文書が求める保存先の確認、出力ディレクトリ作成、レポート・検査JSON・スクリーンショットの整理は、現在の安全境界と承認の範囲内でだけ行う。

### 通常のアクセシビリティレビューとの区別

`reviewing-a11y` はページ、実装コード、デザインの問題発見・重大度・修正案をまとめるレビューである。正式監査の全基準に `Pass` / `Fail` / `NT` / `NA` を割り当てる作業ではない。通常レビューの所見をWCAG適合宣言に読み替えず、正式な適合判断を求められた場合は `auditing-wcag` の範囲・証拠・表を使う。

コードレビューはソースの静的分析である。実行時のキーボード操作や支援技術の動作を確認したことにはならない。デザインレビューも実装の動的挙動を証明しない。色・フォーカス・状態変化・代替テキストなど、設計だけで決められない事項は質問または別の実装検証として残す。

## CLI を使う場合の境界

外部 Skill にある `npx playwright install chromium` や `npx -y @a11y-skills/audit ...` はコマンド例であり、自動導入の許可ではない。既存の承認済み範囲に収まる通常のCLI実行は追加承認なしで進める。`npx` による導入など、承認範囲に含まれない依存の導入・更新・環境変更は別途承認を得てから行う。

実行を許可された場合も、次を揃えてから実施する。

1. 対象URL・ページ・検査範囲・出力先が合意済みである。
2. Node、npm、CLI、Playwright、ブラウザーの実際の版と準備場所を確認する。
3. 準備に使った正確なコマンド、パッケージ、版、ネットワーク利用、承認を記録する。
4. 実行する正確なコマンド、標準出力・標準エラー、終了コードを保存する。失敗コードを成功に丸めない。
5. 出力ファイルを読み戻し、対象URL・時刻・検査名・結果が報告と一致するか見る。
6. CLIが検査した基準だけを結果に反映し、手動・対話・内容判断が必要な基準を別途確認する。できなければ理由付き `NT` と owner を残す。

ローカル Playwright runner の文書は、準備済みの依存を使う明示指定スクリプトのみを対象とし、npm/npx・依存導入・ブラウザー取得を行わない。package または browser が未準備なら、パッケージ名・版・root・ブラウザー場所・ネットワーク利用・正確な準備コマンドを記録して停止する。

## 保存状態の報告

生成した本文は最初は草案である。監査出力の保存先を確認し、書き込みが許可された先に実際に書き込み、そのファイルを読み戻して内容を照合した後に限って「保存済み」と報告する。`Write` が skill metadata に記載されているだけでは保存の証拠にならない。書き込み成功の応答だけで読み戻せていない場合は「書き込み後の確認未完了」とし、失敗時は「未保存」または「保存状態を確認できない」とする。

`ship-learn-next` は計画を常にファイルへ保存し、保存先をユーザーに示すよう要求する。この要求も共有された AGENTS の承認境界に従う。保存先が未確認・未承認なら、内容を草案として示し、保存したと偽らない。
