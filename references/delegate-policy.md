# Delegate Policy Reference

この文書は、`~/.agents/AGENTS.md`に記載された委任方針の詳細である。委任前に親が入力、出力、許可範囲、受入れ条件を確定し、実行経路と権限を確認する。hookは方針を補助するだけで、親や経路を自動判定して実行しない。

## 委任経路と可用性

- 標準モデルは`gpt-5.6-luna`、reasoning effortは`max`とする。
- Claude親はシェル規約に従い、通常は`rtk proxy node ~/.agents/bin/codex-delegate.mjs`でラッパーを起動し、そのNodeプロセスから`codex exec`を使う。rtk proxyを使わない環境では`node ~/.agents/bin/codex-delegate.mjs`を使う。Node経由で実行するため、`.mjs`ファイルに実行ビットは必要ない。ファイルを読み取れること、NodeとCodex CLI、指定モデル、reasoning effortが利用できることを確認した場合だけ委任する。
- ラッパーはユーザー設定を読み込まず、モデル・effort・sandboxを明示する。Codex CLIは`--codex-bin`、`CODEX_CLI_BIN`、macOSのHomebrew版、PATHの順で解決し、利用不能なら`BLOCKED`にする。
- Codex親はnative subagentを使い、`gpt-5.6-luna` / `max`を明示する。native subagentまたは指定が利用可能と確認できない場合は委任しない。
- 経路、モデル、reasoning effortのいずれかが`false`または`unknown`なら、理由を親へ返して親が担当する。旧Codex MCPや別モデル・経路へ自動で切り替えない。
- Claude親のラッパー経路が起動できない場合も、Codex MCP、別の外部ラッパー、tmux paneへ黙って切り替えない。
- 委任先からの再委任は禁止する。

## 選択基準と独立タスク

複雑な原因追跡、依存の強い作業、複数成果物をまたぐ作業でも、親はまず独立した小単位へ分解し、依存関係を明記する。分割可能な読み取り、探索、実装、レビュー、保存後の再検証は、入力・出力・検証条件を固定して委任する。

| 作業 | 担当 | 条件 |
|---|---|---|
| 分解、優先順位付け、横断的な因果統合、設計判断、最終品質判定 | 親 | 常に親が担う |
| 読み取り、抽出、探索、レビュー | `gpt-5.6-luna` / `max` | 対象、出力、受入れ条件を固定し、親が検証できる |
| 実装、保存後の再確認、指定検証 | `gpt-5.6-luna` / `max` | 許可パスと操作が明示され、親が実差分を検証できる |
| 依存関係のない作業 | `gpt-5.6-luna` / `max` | 入出力・許可パスが独立している場合は並列化する |

入力が曖昧、許可範囲を固定できない、受入れ条件を親が検証できない場合は、親が作業する。依存する後続タスクは、親が前段の成果を確認してから始める。同じファイル、state、manifestに触れる作業は並列にしない。

## 権限: 読み取り専用と承認済み書き込み

- 既定は`read-only`。Claude親のラッパーは`codex exec`を読み取り専用sandboxで起動し、Codex親も読み取り専用の権限でnative subagentを開始する。
- 書き込みは、ユーザーがその変更を承認しており、親が対象パス、変更内容、禁止操作、検証条件を委任文に明記した場合だけ`approved-write`として許可する。
- `approved-write`でも許可された作業ディレクトリとパスに限り、Codex CLIでは`workspace-write`を使う。`danger-full-access`や承認回避オプションを使わない。
- `workspace-write`自体は作業ディレクトリ内の許可パスを限定しない。ラッパーは実行後の差分で範囲外変更を`FAILED`として検出するが、変更の発生を事前に防いだり自動復元したりはしない。予防的なパス隔離が必要な作業は親が扱う。
- 実行環境で許可パスを守れない、承認状態が不明、または委任内容が承認範囲を越える場合は起動せず`BLOCKED`を親へ返す。
- 正本、manifest、state、横断的な設計判断、commit、push、merge、PR作成、外部サービス操作は親が担う。個別に明示された作業であっても、それらの権限を委任文だけで付与しない。

## 新規実行とセッション再開

- 新しい目的または独立タスクは、新しい`codex exec`セッションとして開始する。
- `codex exec resume <session-id>`は、同じ目的・成果物・許可パス・承認状態を保った追跡作業に限る。
- `codex exec resume`には`--sandbox`と`-C` / `--cd`がない。これらのフラグをresumeで使えるとは扱わない。ラッパーは、インストール済みCLIが対応する設定方法と子プロセスの作業ディレクトリで、承認済みのsandboxとcwdを再現する。
- resume前に、ラッパーは前回の目的・許可範囲とsession IDを照合し、sandboxを設定値で明示し、子プロセスのcwdを固定する。CLIがこの指定方法に対応しない場合は`BLOCKED`を親へ返す。
- resumeに使うsession IDは、`codex exec --json`のJSONLイベントから親またはラッパーが取得した値に限る。子の文章から推測したID、欠落・矛盾したIDは使わず`BLOCKED`として親へ返す。
- 目的、受入れ条件、許可範囲、承認状態が変わったらresumeせず、新しいタスクとして親が定義し直す。
- 前回が`FAILED`または`BLOCKED`なら自動resume・自動再試行しない。親が原因を確認し、必要なら別タスクとして再定義する。
- 継続が必要な実行では`--ephemeral`を使わない。

## 委任文と結果

委任文には毎回、次を含める。

- Objectiveと受入れ条件
- 固定入力、開始revision、対象ファイル、使用コマンド
- 許可パスと禁止操作
- 権限状態: `read-only`または`approved-write`
- 期待する成果物、出力形式、保存先
- 実行する検証と停止条件
- 親が統合・最終判断を担い、子は指定作業だけを行うこと
- 子から再委任しないこと

結果の状態は`DONE`、`FAILED`、`BLOCKED`のいずれか1つだけとする。

- `DONE`: 指定作業と受入れ条件を満たし、求められた検証結果を添えている。
- `FAILED`: 実行を開始したが、作業または指定検証が失敗した。timeout、異常終了、不正な結果形式、完了状態の欠落も成功とは扱わず、親へ失敗として返す。
- `BLOCKED`: 起動前または継続前に、権限、入力、許可範囲、経路、モデル、effort、session IDなどの不足・不明が判明した。

空応答、`PARTIAL`、未確認、範囲外の変更を`DONE`として扱わない。失敗や停止は親へ返し、自動的に別経路・別モデルへフォールバックしない。

## ラッパーの実行記録

ラッパーは各実行の記録先に次を保存する。

| ファイル | 用途 |
|---|---|
| `events.jsonl` | `codex exec --json`のイベント列。session IDなど実行イベントを読む根拠 |
| `progress.log` | 進捗とエラーの短い記録。prompt本文や秘密情報を含めない |
| `result.json` | 状態、要約、`changedFiles`、`tests`などの結果申告 |
| `run-metadata.json` | model、effort、権限、cwd、時刻、終了コード、session IDなどの実行情報。prompt本文や環境変数は含めない |

## 親による検証と統合

- 親は委任結果を受けたら、実際の差分、変更ファイル、成果物、指定コマンドの終了結果を確認する。子の自己申告だけを根拠にしない。
- `result.json`の`changedFiles`と`tests`は委任先の申告であり、実際の差分とテストコマンド・終了結果で親が照合する。
- `DONE`でも親の検証に通らなければ採用しない。差分衝突や許可範囲外の変更は失敗として扱い、親が判断する。
- 独立タスクはそれぞれの完了時に確認する。依存タスクは前段の成果を親が受け入れてから進める。
- 最終統合、品質ゲートの合否、commit、push、ユーザー報告は親が担う。
