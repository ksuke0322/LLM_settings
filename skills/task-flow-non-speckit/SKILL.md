# Task Flow

通常の作業タスクは、`specs/flow/` をデファクトの置き場として運用する。

## コア方針

- **タスク分割**: AIが適切に分割判断する。
  - 原則は「単一目的・単一成果物・限定的な影響範囲」。
  - 目的が複数ある場合や、フロント/バックなど複数領域にまたがる場合は分割を前提にする。
- **ステータス**: `未着手` / `done` のみ。
- **done定義**: そのタスクで定義した期待値がすべて完了し、ユーザー確認依頼を行い、approve 後にその時点の状態でコミット、タスク更新、main/master へのマージ、作業 worktree の削除まで完了している状態。
- **PR要件**: PRの必須項目は `single-task-pr-policy` と `git-workflow-safety` の規定に準拠。
- **worktree運用**: 各タスクは専用の作業 worktree を作成し、その worktree 上で実施する。

## specs/flow ファイルの最低限構成

- タイトル
- 目的
- 方針（必要なら）
- タスク一覧（1タスク=1PR）
- 各タスクの「期待値 / 対象 / 作業」
- 新規タスクファイルは後述のテンプレートを使う

## 実運用のルール

- 新規タスクは `specs/flow/` に作成する。
- タスク一覧のチェックは `未着手` / `done` のみで管理する。
- 各タスクの着手前に main/master を確認し、タスク用ブランチと専用の作業 worktree を作成する。
- タスク作業は必ずその作業 worktree 上で行い、対象タスク以外の変更を混ぜない。
- タスクの期待値を満たした時点で、まずユーザーに確認依頼を投げる。
- ユーザーに approve されたら、その時点の状態でコミットし、タスク状態を更新する。
- コミットとタスク状態更新後、変更差分を main/master にマージする。リモートレポジトリが存在する場合は直接マージせず、PR経由で反映する。コンフリクトした場合は停止し、解消方針をユーザーに確認する。
- main/master へのマージ後、未コミット差分がないことを確認してから作業 worktree を削除する。
- done化の判断は「期待値の全達成」「ユーザー approve」「承認時点でのコミット」「タスク更新」「main/master へのマージ」「作業 worktree の削除」の全完了を基準とする。抜けがある場合は done にしない。
- 既存のタスク分割が過大/過小な場合、`specs/flow/` で分割提案を先に行う。

## タスクファイルテンプレート

```md
# <タスク名>

## 目的

<このタスクで達成すること>

## 方針

<必要な場合のみ記載>

## タスク一覧

### 1. <タスク名>

- ステータス: 未着手
- 作業ブランチ: <branch-name>
- 作業 worktree: <worktree-path>

#### 期待値

- <完了時に満たすべき状態>

#### 対象

- <対象ファイル/領域>

#### 作業

- <実施する作業>

#### 実施前チェック

- [ ] main/master を確認した
- [ ] タスク用ブランチを作成した
- [ ] 専用 worktree を作成した
- [ ] 作業 worktree 上で作業している

#### 完了チェック

- [ ] 期待値をすべて満たした
- [ ] 対象タスク以外の変更が混ざっていない
- [ ] ユーザーに確認依頼した
- [ ] ユーザー approve を得た
- [ ] approve 時点の状態でコミットした
- [ ] タスク状態を done に更新した
- [ ] リモートレポジトリがある場合は PR 経由で反映した
- [ ] main/master への反映が完了した
- [ ] 未コミット差分がないことを確認した
- [ ] 作業 worktree を削除した
```
