# レビュー品質チェックリスト

試作の出来を毎回ゼロから目視レビューするのはコストが高いため、最低限チェックする観点をリスト化し、レビュー品質を安定させる。テーマが増えるたびに項目を見直す想定。

## A. 構図・画角
- [ ] 完成状態(最も大きい構成)の被写体が、カメラのフレームから欠けていないか
- [ ] 余白(画面の四辺)のバランスが極端に偏っていないか
- [ ] アイソメトリック視点として違和感のない角度になっているか(極端に上から/横からになっていないか)

## B. 構造・接合
- [ ] パーツ同士の接合部に隙間や浮きがないか(床-壁、壁-屋根など)
- [ ] パーツの厚み・プロポーションが「ちゃんとした建物/物体」に見える比率になっているか(紙のように薄い、いかにも仮組みに見えるなどがないか)
- [ ] 各stateでオブジェクト数・ボリュームが単調に増えているか(後の状態で前の状態より要素が減っていないか)

### 構造別クローズアップ検証(必須)
- [ ] `ストーリー設計ワークシート`のオブジェクト一覧表「意図する見た目」列に記載した主要パーツ・装飾品について、各パーツを個別にカメラを近づけて(または上から・横からなど複数角度で)レンダリング/スクリーンショットし、記載した意図(位置・向き・取り付け面)と実際の見た目を1つずつ比較する。
- [ ] 取り付け先(主要構造物)に対して小物が刺さっていないか/浮いていないかを、取り付け先の実際の表面高さ(`bound_box`/`dimensions`)と比較して確認した。
- [ ] 「分かれて見えること」自体が意図の構造的特徴(板の目地・継ぎ目等)は、完成stateの俯瞰レンダリングだけではなく、該当部位のクローズアップで個数/間隔が視認できることを確認した(俯瞰では見えなくてもクローズアップでは見える、という状態は不可)。

## C. マテリアル・質感
- [ ] マテリアルがビューポートのSolid表示だけでなく、実レンダー(Cycles/Eevee)でも正しい色味になっているか
- [ ] 発光部分(窓の灯り等)が意図した強さ・色で見えるか、白飛びや弱すぎがないか
- [ ] テーマ全体の色温度・彩度に一貫性があるか(部分的に作風が浮いていないか)
- [ ] **クール別チェック画像との相違確認**: 自分の目視だけで合否判定しない。`isometric-story-workflow`のステップ8(相違点ゼロまでのループ・hard gate)に従い、文脈を持たない独立サブエージェントに完成stateレンダリングとクール別チェック画像を比較させ、相違点ゼロを確認するまでステップ9に進まない。

## D. 進行・トランジション
- [ ] 未完成状態と完成状態の差が一目で分かるか
- [ ] state切替がハードカットではなく、何らかの動き(成長・落下・フェードイン等)を伴っているか
- [ ] 動きの種類がパーツの役割に対して自然か(地面に立つものが地面から生える、上に乗るものが上から来る、灯りが点灯するなど)
- [ ] 全体を通して「常に何かが動いている」状態が保てているか(完全に静止する区間が長すぎないか)

### チェック手順(必須)
- [ ] 各stateの開始フレーム・終了フレーム・遷移中間点の最低3点を必ずスクリーンショットで確認する(境界フレームだけでは途中で固まっている/意図しない状態になっていることに気づかない)。
- [ ] 1フレームだけではなく複数フレームを比較し、値が連続的に変化しているか(途中で固まっていないか)を確認する。
- [ ] **frame1で、まだ初出していないすべてのパーツ(他stateのオブジェクト)が本当に見えていないこと**をスクリーンショットで確認する。発光オブジェクトはEmission Strength=0でも不透明な黒い物体として表示されるため、Strengthアニメーションだけでは不十分(`hide_viewport`/`hide_render`のCONSTANTキーフレームが別途必要)。実際にこの事象が原因で発光球が早期フレームから見えてしまう事故が発生した(`blender-isometric-rules` SKILL.md 6章参照)。
- [ ] **新規に`hide_viewport`/`hide_render`キーフレームを追加・修正した箇所すべてについて、対応する出現トランジション(成長・落下・フェードイン等)がペアで実装されているか**を確認する。「見えない事故」を直す際にhideキーフレームだけ追加してトランジションを付け忘れ、別のstateの境界で瞬間的にポップインするハードカット事故が2度発生している(`blender-isometric-rules` SKILL.md 6章「【禁止】hide_viewport/hide_renderの単体追加」参照)。境界フレームの前後数フレームを比較し、サイズ・位置が連続的に変化しているか(突然フルサイズで出現していないか)を確認する。

## E. 体験としての説得力
- [ ] 完成時に「自分の集中でひとつ完成させた」と感じられる見た目になっているか
- [ ] 作業中(集中画面想定)の演出が、視線を奪いすぎていないか
- [ ] テーマの主役だけでなく、周辺の余白(背景・環境)がテーマの世界観と合っているか

## F. 量産適性
- [ ] パーツの命名・Collection構造が後から自動化・流用しやすい形になっているか
- [ ] 座標やサイズが共通変数から導出されており、手打ち値に依存していないか
- [ ] 同じ型を別テーマに適用したときに、大きな手直しが要らないか

## 今後の検討事項
- チェックリストの各項目を、できるだけ目視ではなくコードでの自己検証(bounding box比較、レンダー画像のピクセル解析等)に置き換えていきたい。
- テーマごとに固有のチェック項目(例: 流体シミュレーションを使うテーマなら「シミュレーションが安定して破綻していないか」)を追加していく前提のドラフト。
