# 開発ワークフロー

## 開始・承認と方針変更

- 承認範囲、作業開始、方針変更は `AGENTS.md` を正本として扱う。この skill は承認手順を重ねて作らない。
- 計画や方針への了承は作業開始指示ではない。明示された作業開始指示を受けた後、承認範囲内で進める。
- 同じ承認範囲内の作業では追加承認を求めない。承認範囲を超える変更が必要なとき、または方針変更・計画失敗が起きたときは停止し、`AGENTS.md` に従って確認する。
- 既に承認された範囲内のテスト追加・修正にも、追加承認を求めない。

## 変更種別と検証

| 変更種別 | 進め方と検証 |
| --- | --- |
| 動作変更・動作影響設定 | 期待する振る舞いを示すテストを実装前に書き、意図した失敗理由の Red を確認してから最小変更で Green にする。動作に影響する設定変更も対象とする。詳細は `skills/test-driven-development/SKILL.md` を参照する。 |
| 挙動維持リファクタ | 既存テストを実行して回帰を確認する。テストがない場合は変更のリスクとテストの必要性を確かめ、追加が承認範囲外なら `AGENTS.md` に従って確認する。 |
| テストの追加・修正 | 承認範囲内で、仕様上の期待する振る舞いをテストに表し、Red がその要件または対象の欠陥を示す正しい失敗か確認する。必要最小限の実効的な条件を検証し、テストを弱めて実装の失敗を隠さない。 |
| 文書・動作非影響の設定・生成物 | 変更内容に合う検証を行う。文書は要求事項、参照先、リンク、例を確認し、設定や生成物は該当する形式・生成元との整合を確認する。ユーザーまたは現在のセッションが全件検証を指定した場合は、その範囲を維持する。文書変更だからという理由で検証を省略しない。 |

TDD の Red では、期待する振る舞いをテストに表し、失敗がその要件を検出していることを確かめる。Green はその失敗を解消する最小変更とし、必要な検証が通った後に挙動を変えない範囲で整理する。

## 検証コマンドの根拠と失敗時の扱い

- 検証前に、対象に近い `package.json`、`pyproject.toml`、`Makefile`、README、CI 設定など、そのリポジトリの正本情報からコマンドを確認する。各実行について、明示されたコマンド、根拠、作業ディレクトリ、対象範囲を記録する。
- ユーザーまたは親が承認範囲内で明示した実行コマンドも根拠として使える。その指示と対象範囲を記録し、設定に同じ記載がないことだけを理由に再確認を求めない。
- `skills/test-driven-development/SKILL.md` や `test-fixing` にある `npm test`、`make test`、`uv run pytest` などは外部の例である。ローカルの変更種別と正本情報を優先し、例をそのまま実行しない。
- test と lint など複数の検証コマンドが併存することだけでは停止しない。対象範囲と正本情報から適用する候補を絞れない、根拠がない、または記載が矛盾する場合は `確認不能` として停止し、確認する。対象範囲外の隣接 package は根拠にしない。既定のコマンドを推測で実行せず、別コマンドへの自動切替、依存の自動導入、未確認コマンドの自動再試行をしない。
- 失敗は、アサーションの失敗、構文・起動の失敗、依存・入力・環境の不足などに分けて原因を確認する。承認範囲内で原因を直した後は、同一の明示コマンドを再実行する。方針や対象範囲が変わる場合は停止し、親に確認する。
- `test-fixing` skill は失敗原因の分類を補助するために使い、自動修正や自動再試行の根拠にしない。TDD の手順詳細は `skills/test-driven-development/SKILL.md` に従う。

## 差分確認と報告

- 作業後は許可された変更範囲と検証結果を照合する。Git 操作、PR、merge、cleanup は `AGENTS.md` と `skills/git/SKILL.md` に従う。
- 変更したファイル、実行したコマンドと根拠、検証結果、未確認事項、残る制約を報告する。失敗・未確認を成功として扱わない。
