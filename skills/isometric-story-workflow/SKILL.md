# テーマ制作ワークフロー

## 位置づけ

- 本スキルは「いつ何を、どの順序で、どのレベルの厳密さで決めるか」を扱う。「Blenderでどう正しく作るか」は `blender-isometric-rules` スキルを参照する(ステップ6以降で必ず併用する)。
- 用語定義(必読): テーマ > ストーリー > クール > 映像 の階層。
  - テーマ: 世界観のまとまり(例: 小さな街)。
  - ストーリー: テーマ内の1つの物語ライン。複数クールの連作(基本2〜3クール)で構成される。
  - クール: 1回のポモドーロ(25分)で完結する単位。**クール1はゼロから完成させ、クール2以降は前クールの完成形をそのまま引き継いでさらに発展させる(ゼロから作り直さない)**。
  - 「ストーリーが切り替わる」ときは対象がゼロから始まる。「クールが切り替わる」が同じストーリー内なら前クールの完成形を引き継ぐ。

## ワークフロー全体

1. **(ストーリー単位)** 参考イメージ収集
2. **(ストーリー単位)** オブジェクト一覧表・寸法比例表等の作成(下記「ワークシート」節)
3. **(ストーリー単位)** 共通の寸法変数・カメラ・トランジションの型を一括設計
3.5. **(ストーリー単位)** 世界観リファレンス画像を1枚生成し、設計書ページに添付
4. **(ストーリー単位)** 人間レビュー(設計書ページ。テキスト+世界観リファレンス画像が対象) — 必須の停止点
5. **(ストーリー単位)** テーマ固有差分(寸法変数・オブジェクト一覧・state構成)を`references/prompt-db-template.md`に従ってBlender用プロンプトDBへ保存(ルール本体は再掲しない)
6. **(クール単位ループ)** 設計書ページ+プロンプトDBページを明示fetchし、クール用ファイルを準備。あわせてクール別チェック画像を1枚生成
7. **(クール単位ループ)** fetchしたテーマ固有差分+クール別チェック画像+`blender-isometric-rules`スキルで該当クールを実際に制作
8. **(クール単位ループ)** `blender-isometric-rules`の`references/review-checklist.md`に基づく自己レビューに加え、レンダリング静止画とクール別チェック画像を比較
9. **(クール単位ループ)** 人間が目視レビュー — 必須の停止点
10. **(クール単位ループ)** 直前クールまでの通し再生を軽く確認(推奨)
11. 次のクールへ進む(6に戻る。ステップ3.5・5の共通設計は再利用)
12. 全クール完了後、ストーリー全体を通しで動画書き出し・最終レビュー

ステップ1〜5(3.5を含む)はストーリーごとに1回だけ実施し、以降のクールループでは再利用する。

### ステップ1: 参考イメージ収集
- テーマ名そのもの(例: 「lighthouse」)でWebSearchし、「isometric」等の修飾語は付けずに5〜8枚程度確認する(アイソメ表現自体ではなく、テーマに実在しそうなオブジェクト・雰囲気・配色を集めるため)。
- 画像はスクラッチ領域に一時保存して確認するだけにし、永続化やBlenderへの直接取り込みはしない。
- 確認した内容を「実在しそうなオブジェクト」「雰囲気・配色の傾向」「質感の傾向」の3点に簡潔にまとめ、ステップ2・3の初期値として使う。言語化メモは設計書ページの一部として残す。
- アイソメ表現そのもの(構図・ビジュアルスタイル)は参考画像の表現に関わらず本ワークフロー・`blender-isometric-rules`のルールに従う(ビジュアルスタイルはトイクレイ調/フラットトゥーンの2択から選ぶ。**いつ確定するか**: ステップ1で方向性を仮決めし、ステップ4の人間レビューで確定する。毎回都度確認が必須ではなく、ここで仮決め→レビュー時確定という流れに従う)。

### ステップ2・3: ワークシートを埋める

下記「ワークシート: 記入ルール」をすべて満たすまでステップ4へ進まない。実際に埋めた内容は、ワークシートを複製して設計書DB配下にストーリーごとの新規ページとして作成する(テーマ名とストーリー名を含めたページタイトルにする)。

### ステップ3.5: 世界観リファレンス画像生成
- 目的: スタイル・配色・雰囲気が全クールを通じて一貫しているかを、テキストだけでなく画像でも確認できるようにする。クール単位の実装チェックには使わない(クール2以降の要素も含む「最終形」の画像のため)。
- 入力: ストーリー全文(一言要約+各クールで完成するものの説明。Notion「ストーリー設計ワークシート」相当)と、ステップ2・3で確定した設計内容(オブジェクト一覧表・質感タイプ・World/ライティング設計表・配色・画面方針メモ)。クール1・クール2以降の区別なく、ストーリー全体の完成形を1枚に統合してよい。
- 生成手段: 現時点でこの環境にテキスト→画像の専用ツールは無いため、computer-useでCodex等の隣接アプリにプロンプトを送って生成する(利用可能な他の画像生成手段があればそれでよい)。
- 生成後、設計書ページに画像を埋め込み/添付する(ステップ4の人間レビューの対象に含めるため)。ローカルにも`test_gen_ai/<ストーリー名の英文表記>/ref/world_reference.png`として保存する。

### ステップ4: 人間レビュー
- 設計書DB配下のページを対象に、生成を始める前に設計の方向性・曖昧さをここで確定させる。**ステップ3.5で添付した世界観リファレンス画像もレビュー対象に含める**。承認なしで次に進まない。

### ステップ5: テーマ固有差分の記録
- ルール全文(`blender-isometric-rules`)を都度コピーしてプロンプト全文を作る必要はない(Skillが実装時に自動的に効くため、Notion側に再掲すると二重管理になる)。
- 代わりに、**寸法変数・オブジェクト一覧・state構成**等、そのテーマ固有の差分だけをBlender用プロンプトDB配下に新規ページとして保存し、設計書ページと相互リンクする。これは「常に効くべき共通ルール」ではなく「このテーマだけの一回性データ」なので、Skillに溜め込まずNotionに置き、ステップ6で明示的にfetchして使う。
- 保存する内容は`references/prompt-db-template.md`のテンプレートに**全項目**従う(空欄・TBD不可)。曖昧さ・抜け漏れを残したまま保存してはならない。テンプレート末尾の「保存前の最終確認」チェックリストを実際に1項目ずつ確認してから保存する。

### ステップ6: クール用ファイルを準備
- **必ず最初に**、対応する設計書ページと、ステップ5で保存したBlender用プロンプトDBページ(寸法変数・オブジェクト一覧・state構成)をNotionから明示的にfetchする。テーマ固有データはSkillのように自動では効かないため、ここで取りに行く工程を省略してはならない。
- 作業ディレクトリは`/Users/sawairikeisuke/Documents/Blender/isometric/test_gen_ai/<ストーリー名の英文表記>/`を新規作成し、その配下で作業する。`.blend`はディレクトリ直下に分かりやすい名前(例: `lighthouse.blend`)で保存し、レンダリング結果は`output/`サブディレクトリに置く。
- クール1: ストーリー用の新規`.blend`ファイルを作成する。
- クール2以降: 前クール完成時の`.blend`を複製し、新しいクール用ファイルとして保存する(ゼロから作り直さない)。複製後は`blender-isometric-rules`7章のルールR(クール間引き継ぎ)を必ず適用する。
- **クール別チェック画像の生成**: オブジェクト一覧表の「初出クール」列が**当該クール以下**(前クールまでの完成要素+今回新規追加分)の要素だけに絞ってプロンプトを組み、1枚生成する。未来のクール(まだ存在しないはずの要素)は絶対に含めない。生成手段はステップ3.5と同じ。保存先: `test_gen_ai/<ストーリー名の英文表記>/ref/cool<N>_reference.png`。
- **PolyHaven対象の適用確認**: ステップ2・3で確定したPolyHavenアセットを`blender-mcp`の`download_polyhaven_asset`/`set_texture`で実際にダウンロード・適用し、シーンの質感・色味と合うか確認する。問題なければそのまま採用する。**質感・色味が合わない、既存の配色方針と衝突する等の問題が見つかった場合、AIが自己判断でプロシージャルへ差し替えてはならない**。一旦作業を止め、具体的に何が合わないかをユーザーに報告し、フォールバックの可否を確認してから先に進む。

### ステップ7: 制作
- ステップ6でfetchしたテーマ固有差分(寸法変数・オブジェクト一覧・state構成)と`blender-isometric-rules`スキルを組み合わせ、`blender-mcp`経由で該当クールを実際に制作する。
- ステップ6で生成したクール別チェック画像を質感・装飾密度の参照として見ながら作り込む(寸法・配置等の構造的なルールは`blender-isometric-rules`を優先し、画像は質感・装飾のリッチさの目線合わせに使う)。

### ステップ8: 自己レビュー(相違点ゼロまでのループ・hard gate)

**背景(なぜループ必須か)**: 構造チェック(接合・接地・カメラフレーミング等、コードで機械的に検証できる項目)は通っているのに、質感・装飾密度・World設定のリッチさがクール別チェック画像(ref)に対して大きく見劣りする状態のまま「自己レビュー完了」と報告し、ユーザーの目視指摘で初めて発覚した事故が実際に起きている。原因は2つ: (1) ステップ7の制作でref画像を実際の作り込み目標として使わず簡易プリミティブで済ませたこと、(2) ステップ8の自己レビューが「相違点リストを書いて終わり」という一回限りの確認に留まり、相違点が残ったままステップ9に進めてしまったこと。さらに、製作した本人(同一セッションのAI)が自分の成果物を採点すると、相違点を過小評価する自己採点バイアスがかかる。この2つを構造的に防ぐため、ステップ8は**相違点が0になるまで完了しないループ**とし、**比較判定はこのセッションの文脈を持たない独立したサブエージェントに行わせる**。

手順:
1. 完成state(最終frame)の静止画レンダリングを行う。動画レンダリングはこの静止画チェックを通過した後にのみ行う(コストが高いため、判断のたびに動画を作らない)。
2. `blender-isometric-rules`の`references/review-checklist.md`(A〜F節+構造別クローズアップ検証)に基づく構造的な自己レビュー(接合・接地・フレーミング等、コードで機械的に検証できる項目)を行う。
3. **独立レビュアーによる相違点列挙**: `Agent`ツールで`Explore`または`general-purpose`サブエージェントを起動し、(a)完成state静止画レンダリングのファイルパスと(b)ステップ6のクール別チェック画像のファイルパスの2つだけを渡す。このセッションでの作業経緯・意図・既知の課題は一切共有しない(製作者の手心が混入するため)。プロンプトには「2枚の画像を見比べて、質感・ジオメトリのディテール・装飾密度・配色/ライティング・構図の観点で具体的な相違点を箇条書きで列挙してほしい。一致していればその旨だけ報告してほしい」という主旨のみを与える。
4. サブエージェントが相違点を1件でも報告した場合: その相違点を実際に修正し、再レンダリングして手順3に戻る(リストを記録して次に進むことは禁止。**相違点リストはユーザーへの報告物ではなく、ループを回すための内部ワーキングデータ**として扱う)。
5. サブエージェントが「相違点なし」と判定するまで3〜4を繰り返す。実用上の許容差(色の微妙な階調差など軽微なもの)はサブエージェントの判定基準に委ねてよいが、構造的・量的に明らかな差分(ディテールの有無、装飾密度、構図の寸法感等)は妥協しない。
6. 収束しない、または同じ相違点が何度も再発する場合はループを打ち切らず、ユーザーに状況(何が・何回・なぜ解決できないか)を報告して判断を仰ぐ。
7. ステップ9に進めるのは、独立サブエージェントが「相違点なし」と判定した最終レンダリングのみ。

### ステップ9: 人間レビュー
- 静止画でのレビューを基本とし、動きの確認が必要な場合のみ短尺プレビュー(動画)を見る。**動画レンダリングは必ず明示的な指示があった場合のみ行う**(静止画OKの後にユーザーから動画レンダーの指示があるまで作らない)。

### ステップ10: 通し再生確認(推奨)
- クールが増えるほど前クールとの接続不整合に気づきにくくなるため、強く推奨する。

### ステップ12: ストーリー全体の最終レビュー
- 全クール完了後、通しで動画書き出し・最終レビューを行う。

## ワークシート: 記入ルール

ステップ2・3で実際に埋める4つの表(オブジェクト一覧表/寸法比例表/Collection構成表/World・ライティング表)と配色・画面方針メモについて、詳細な列定義・カタログ・記入ルールは `references/worksheet-rules.md` を参照する。空欄や「TBD」が残った状態でステップ4に進んではいけない。目次:

- オブジェクト一覧表(名前/分類/初出クール/前クール完成物との関係/動き方分類/登場演出タイプ/強化技法(a〜d)/サイズ比較対象/意図する見た目)
- 背景ディテール(配置方法・種類数・配置平面・接地ルール)
- 寸法比例表(`STAGE_EXTENT`・背景ディテールとの衝突回避)
- Collection構成表(`common_environment`)
- 質感タイプ・構造タイプ・アセット方針表(PolyHaven選定)

## ステップ4(人間レビュー)に進む前の曖昧さチェックリスト

以下すべてにチェックが入らない場合、ステップ4に進んではいけない。

- [ ] オブジェクト一覧表に空欄・TBDがない
- [ ] 動き方分類が全要素について4分類のいずれかに割り当てられている
- [ ] 「登場演出タイプ」が全要素(主体・周辺要素)に割り当てられており、同一クール内で主体・周辺要素同士の重複がない
- [ ] 各クールに強化トランジション対象が最低1要素あり、「強化技法(a〜d)」列で具体的な手法が明記されている
- [ ] 「サイズ比較対象」列に列挙された全ペアで、サイズが最低30〜50%以上ばらついている
- [ ] 各stateに背景ディテールが最低15〜30個(カメラから視認可能な個数で)配置されている
- [ ] 背景ディテールの種類が最低5種類以上ある
- [ ] 各背景ディテールの種類ごとに配置平面が設計段階で明記されている
- [ ] 各背景ディテールのZ位置が接地ルール(raycastスナップ)に従い、指定された配置平面以外の場所に出現していないことをレンダリングで確認した
- [ ] 背景ディテールの代表寸法が近接主要構造物基準変数の25%〜55%の範囲に収まっている
- [ ] 寸法比例表の比率列がすべて「他の変数からの比率」で埋まっており、絶対値の直接入力がない
- [ ] STAGE_EXTENTが定義されており、各クールの追加要素がその範囲内に収まることを確認した
- [ ] 複数クール構成の場合、クール2以降の寸法もすべてクール1主体の定数からの比率になっている
- [ ] 複数クール構成でクール2以降に主要構造物を追加する場合、引き継いだ背景ディテールのSelectionマスクに除外ゾーンが追加されている
- [ ] Collection構成表にcommon_environment相当の常時表示Collectionが存在する
- [ ] 各要素の「前クール完成物との関係」が一言で言える
- [ ] 各要素について「意図する見た目(1文)」が記入されている(特に装飾品・小物・取り付け付属品)
- [ ] 質感タイプが全要素に割り当てられている(最低2種類以上)
- [ ] World・ライティング設計表に空欄がない
- [ ] 配色・画面方針メモに空欄がなく、ビジュアルスタイルがトイクレイ調/フラットトゥーンのいずれかに確定している
- [ ] 構造タイプが全要素に割り当てられている(不要な要素は「—」明記)
- [ ] 内包する発光オブジェクトがある要素は半透明対象として明記されている
- [ ] アセット方針が全要素に割り当てられ、PolyHaven対象は`api.polyhaven.com`での実検索により実在確認済み(推測のアセット名でないこと)。該当なしの場合は「プロシージャルで代替」と明記されている
- [ ] 複数クール構成の場合、前クール共有マテリアルの要否が全要素に明記されている
- [ ] 世界観リファレンス画像(ステップ3.5)が生成され、設計書ページに添付されている

## Notionとの役割分担

- 本スキルは「手続き的な手順・記入ルール」を扱う。実際に各ストーリーで埋めた表・生成された設計書・Blenderプロンプトの実体は、引き続きNotionの設計書DB/Blender用プロンプトDBに保存する(複数ストーリーを横断した人間レビュー・参照のため)。
- ステップ6以降のBlender実装ルールは`blender-isometric-rules`スキルを必ず併用する。
