# 日替わりと実行状態

## 保存場所

通常の実行時に `~/.local/state/blue-archive-daily/state.json` を必要に応じて作成・更新する。スキルのソースやGit管理対象へ資源・日次ログを書き戻さない。現在のアカウント名を照合し、別アカウントの記録を使わない。並行実行中なら二重操作を避け、既存実行の終了を待つ。

日付はAsia/Tokyoのゲーム内日次更新を基準にする。初回はゲームのヘルプ・更新表示で境界を確認し、確認した時刻を記録する。PCの暦日だけで日付を決めない。更新境界が不明、または日付をまたぐ可能性がある場合は、ミッション状態を確認するまで資源を消費しない。

## 最小構造

JSONには次を保持する。作成時に過去の会話を今日の完了として初期化しない。

- `schema_version`：1
- `account_name`、`timezone`、`reset_hour`：画面と照合したアカウント・日次更新条件
- `rotations`：hard / bounty / exchange ごとに、設定リストと次の対象index
- `days`：ゲーム内日付ごとの固定割当、各項目の実行前後進捗、状態、確認した消費
- `verification`：指名手配・学園交流会の実地検証結果とステージ名・日時

項目状態は `not_started / pending / partial / completed / already_completed / blocked / uncertain` を区別する。保存前のJSONを読んで、今回変更する項目だけ更新する。原子的な置換で保存する。保存に失敗したら新しい資源消費を始めない。

## 対象の決め方

1. 初回の次indexはそれぞれ0。ゲーム内日付の割当が既にあれば、それを再利用する。
2. 未割当の日は、各種類の次indexから対象を割り当て、出撃・掃討前に保存する。その日の途中でリストや対象を自動変更しない。
3. Hardは3/3到達、指名手配・学園交流会は選択対象で残チケットを使い切ったことを確認したら、次indexを1つ進める。進めるのはその種類について1日1回だけ。翌日になってから次の対象を使う。
4. 失敗・一部成功・資源不足なら次indexを進めない。翌日も未完了の対象から始める。
5. Hardは実行開始前に既に3/3なら追加周回せずalready_completedを記録し、次indexも進めない。指名手配・学園交流会はミッション達成済みでも残チケットがあれば当日の対象で使い切る。残チケット0なら追加実行せず、過去の周回先や次indexを推測しない。当日除外した種類も次indexを進めない。
6. 過去日付の処理をやり直したり、未実行日数分をまとめて消費しない。

## 再開と結果不明

消費直前にpendingを保存し、対象、実行前の進捗・資源、予定回数を記録する。結果と進捗を確認後、観測した消費と状態を更新する。

- 同日再実行：当日の除外指示を最初に再適用する。Hardなど回数指定の項目は最新のミッション進捗から残り回数を算出する。指名手配・学園交流会は実際の残チケット数を使う。ミッション確認省略の指定時は、今回確認済みの操作記録と結果・資源を使い、未確認の完了を推測しない。
- 例：Hardが1/3なら当日の固定ステージを2回だけ。3/3なら実行しない。
- pendingやuncertainが残っていたら、ミッション進捗・資源・結果表示を照合する。増加分が確認できれば反映し、必要な残回数のみ進める。
- 未達成なのか反映遅延なのか区別できない、ユーザー操作が並行している、ミッションが表示されず消費を確定できない場合は、その項目を再実行せず報告する。
- 状態ファイルと画面が矛盾したら画面を再確認する。完了記録があるのに未達成表示の場合、別日・別アカウント・更新境界の問題を解消するまで消費しない。
