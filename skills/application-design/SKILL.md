# アプリケーションデザイン

対象はアプリの UI/UX。既存アプリの修正では、そのデザインシステム、共通部品、利用者の操作習慣と依頼範囲を先に確認する。局所修正から全体の再設計へ広げない。

## 判断の順序

1. 利用者の目的、主要操作、必要な情報と状態を整理する。不明な前提が判断を左右する場合だけ確認する。
2. 情報の階層、配置、余白、グルーピング、操作の見つけやすさで理解できる構成を作る。
3. 説明文や補助ラベルを追加する前に、構成や操作名で解決できるか確かめる。画面を見れば分かる説明、同じ情報の重複、実装都合だけの文言は省く。
4. 入力条件、単位、エラーの修正方法、操作の結果や取り消せない影響、未確定・不明な状態、アクセシビリティに必要な名前や説明は残す。短さのために必要な情報を隠さない。
5. 依頼に関係する通常・空・読込中・失敗状態と主要操作を、実際の画面またはモックで確認する。文字量、画面幅、拡大表示、入力方法が変わっても情報と操作を保つ。

## 必要な参照を選ぶ

- Web アプリ: [Web の指針](references/web.md)。既存のデザインシステムを優先し、Material を一律に適用しない。
- iOS・macOS アプリ: [Apple プラットフォームの指針](references/apple-platforms.md)。Apple 固有の判断は HIG を主参照とする。
- 対象に関係する参照だけ読み、細かな仕様や迷う判断は公式の該当ページで確認する。取得できなければ未確認と記録し、確認したことにしない。

## 他のスキルとの分担

- Figma の制作・取得・コード変換は該当する Figma スキルの手順に従う。このスキルはツール操作の承認を与えない。
- SwiftUI の実装・API・性能は `swiftui-pro` を標準とし、専門的な補足は `swiftui-expert-skill` を使う。明示されたスキル選択と既存の運用方針を守る。
- AppKit など SwiftUI 以外の実装では、対象フレームワークの公式資料とプロジェクトの実装規則を使う。存在しない専用スキルを前提にしない。
- Web のアクセシビリティの問題発見は `reviewing-a11y`、全達成基準の正式な適合判定は `auditing-wcag`。個別監査の計画は `planning-wcag-audit`、組織全体の改善計画は `planning-a11y-improvement` に分ける。ネイティブ UI は対象 OS の指針と実際の支援技術で確認し、Web 向け監査だけで適合を保証しない。

## 完了時

主要操作と関連状態の確認結果、残る問題、確認できなかった環境を報告する。指示の読み合わせだけで、自動選択・生成品質・アクセシビリティ適合を検証済みとしない。
